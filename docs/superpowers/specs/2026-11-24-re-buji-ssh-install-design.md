## 1. なぜ作るか

レンタルサーバーへの設置は、今は 12 の段がある。zip を取る、展開する、FTP で約 1,500 ファイルを上げる（置き方は 2 通り）、`storage/` の権限を直す、そのあとブラウザの初期設定が 8 段（環境、設置の鍵、DB、最初の管理者、メール、返信、公開されていないことの確認、仕上げ）、最後にサーバーの管理画面で cron を登録する。

作者の見立て：
- **zip の展開から初期設定までが、いちばんの壁。** ここをどれだけ簡単にできるかが、最大の課題。**[決定]**
- **入れるのは技術者。** GitHub でしか配っていないので、技術者以外が入れることはない。**[決定]**
- **比べる相手は Docker。** 中身が分かる人でも、Docker に比べて手順が多すぎる。**[決定]**

そこで、SSH で入れるサーバーでは、スクリプトを 1 回流せば、設定まで済んだ Re:無事 ができるようにする（Docker と同じ形）。**[決定]**

### 成功とは

- SSH で入れる技術者が、**コマンド 2 つ**（スクリプトを取る、流す）を打ち、質問に答えてテストメールに返信するだけで、設置を終えた Re:無事 を得る。
- 後に残る手作業は、見張りの URL を監視サービスに登録することと、`crontab` を SSH で書けないサーバーでは、管理画面に cron を 1 行登録すること。Docker の本番の手順（`.env` を書く、`docker compose up -d`、`admin:create`、`check --wait-reply`、見張りの URL を登録する）より少ない。
  - SSH で `crontab` を書けるのは、4 社のうち、さくらのレンタルサーバだけの見込み（builder が各社の公式の文書で確かめる。3.8）。案 B を示したときも「`crontab` が使えるサーバーなら」としていた。

### 目標

- SSH で流す設置スクリプトが、ファイルを置くところから、DB、最初の管理者、メールの設定、返信の確かめ、公開されていないことの確かめ、cron の登録までを済ませる。**[決定]**
- 設定は対話で聞く。`--config` で渡したファイルからも読む。ファイルの名前は Docker の `.env` と同じ（`REBUJI_SMTP_HOST` など）。**[決定]**
- ブラウザの初期設定と同じ確かめ（テストメールへの返信、データベースや設定がウェブから読めないこと）を通らないと、設置を終えない。**[判断]** 元の設計 6.3 の決まりで、ここを省くと、メールが届かない、個人情報が読める、のまま動き出す。
- この方法で入れたものは、`bin/upgrade.sh` で上げられる。公開ディレクトリを覚えておくので、`--public` を渡し直さなくてよい。**[判断]** 設置と更新が同じ道具立てでそろう。

### 目標にしないこと

- SSH の無いサーバー（ロリポップのエコノミー・ライトなど）。今の FTP と画面の初期設定がそのまま受け持つ。**[決定]**（残す）
- 人がいなくても終わる設置。返信を確かめるのに人が要る。**[判断]**
- root や sudo が要る作業、VPS を用意すること。VPS は Docker が受け持つ。**[判断]**
- 監視サービス（UptimeRobot など）への登録を、スクリプトが代わりにすること。**[判断]** 外のサービスのアカウントが要る。
- 版を上げること。`bin/upgrade.sh` が受け持つ。**[判断]**
- 画面で設置したものを、この方法で設置し直すこと。**[判断]**

### やってはいけないこと（アンチゴール）

- 公開ディレクトリにある、ほかのサイトのファイルを上書きすること。
- 聞かずに `crontab` を書き換えること。ほかの行を消す、変える、同じ行を二重に足すこと。
- 確かめが済む前に「設置済み」（`storage/config.php` の `installed_at`）になること。設置済みになると、画面の初期設定と、公開されていないことを確かめる手がかり（`/install/probe/…`）が閉じる。
- パスワードが、コマンドの引数（`ps` で見える）、シェルの履歴、ログ、ほかの利用者に読めるファイルに残ること。
- FTP と画面の初期設定を壊すこと。Docker での設置の動きを変えること。

## 2. 案

作者に示した 3 つの案（2026-11-24）：

| 案 | 中身 | 残る手作業 | 作る量 |
|---|---|---|---|
| A | SSH で設置スクリプトを流し、ファイルを置くところまで済ませる（`bin/upgrade.sh` と同じ仕組み）。初期設定は今の画面のまま | 画面の初期設定、cron と監視の登録 | いちばん少ない |
| **B** | A のスクリプトが、設定（DB、管理者、メール、返信、公開の確かめ、cron）までその場で済ませる | 返信すること、監視の登録 | A より多い（画面の各段をコンソールでもできるようにする） |
| C | PHP ファイルを 1 つだけ FTP で上げ、そのファイルが zip を取って展開する | 画面の初期設定、管理画面での cron の登録 | 中くらい。SSH の無いプランにも効く |

**B に決まった。** **[決定]** 理由：入れるのは技術者なので SSH が前提で困らない。B なら手順が Docker と同じか、それより少ない。`bin/upgrade.sh` と同じ道具立てなので、設置と更新の流れがそろう。

設定の渡し方は、「対話だけ」と「対話＋ファイル」から、**対話＋ファイル**に決まった。**[決定]** ファイルなら、やり直しのたびに打ち直さずに済む。Docker の `.env` と同じ名前なので、書き方を覚え直さずに済む。

文言と細かい順番は builder に任せる（7 章）。守ること：
- 既定は設定の画面と同じ値にし、Enter だけで受け入れられる。**[判断]**
- ファイルにある値は聞かずに使い、何を使ったかを 1 行で示す（パスワードは示さない）。**[判断]**
- パスワードは画面に出さない（`ConsoleIo::secret()`）。**[判断]**

- **人が答える問いは、返信を待つ前に全部済ませる**（cron の問いも）。返信を読めたら、その先は何も聞かずに最後まで進む。**[判断]** 設置を終えた（`installed_at`）あとで問いを待っているときに SSH が切れると、流し直しても「設置済み」で止まり、続きができない

### 3.2 コマンド

```
sh install.sh [--public DIR] [--root DIR] [--url URL] [--config FILE] [--version X.Y.Z] [--zip FILE]
```

| 引数 | 意味 |
|---|---|
| `--public DIR` | 公開ディレクトリ。`public/` の中身だけをここに置く（3.4）。渡さなければ、パッケージ全体を `--root` に置き、`--root` が公開されている形になる |
| `--root DIR` | 本体を置く場所。`--public` を渡したときの既定は `~/re-buji`。名前は `bin/upgrade.sh` の `--root` にそろえる |
| `--url URL` | 公開する URL。渡さなければ聞く |
| `--config FILE` | 設定ファイル（3.3） |
| `--version`、`--zip` | `bin/upgrade.sh` と同じ（その版を入れる、サーバーに置いた zip から入れる） |
| 環境変数 `PHP` | 使う php。渡さなければ探す（3.5） |

**[判断]** 「どこに置くか」（場所と URL）は引数に、「何を設定するか」（DB とメール）はファイルに、と分ける。ファイルは Docker の名前だけにそろえ、Docker に無い名前を足さない。

**[判断]** `--public` と `--root` のどちらも渡さなければ、何も取らずに止まり、2 つの置き方を示す。何も渡さずに既定の `~/re-buji` に全体を置くと、ふつうは公開されていない場所なので、取って展開したあとで、公開の確かめで止まるだけになる。前の回が覚えた公開ディレクトリがあれば（3.7）、それを使う。

### 3.3 設定ファイル

- 形は Docker の `.env` と同じ：1 行に `名前=値`。`#` で始まる行と空の行は読まない。値が空の行（`名前=`）は、書いていないのと同じ（`.env.example` の決まりと同じ）。`.env.example` に出てくる書き方は、すべて読めること。**[判断]**
- 読む名前：
  - DB：`REBUJI_DB_DRIVER`、`REBUJI_DB_HOST`、`REBUJI_DB_PORT`、`REBUJI_DB_NAME`、`REBUJI_DB_USERNAME`、`REBUJI_DB_PASSWORD`
  - 送信：`REBUJI_SMTP_HOST`、`REBUJI_SMTP_PORT`、`REBUJI_SMTP_ENCRYPTION`、`REBUJI_SMTP_USERNAME`、`REBUJI_SMTP_PASSWORD`、`REBUJI_MAIL_FROM_ADDRESS`、`REBUJI_MAIL_FROM_NAME`
  - 受信：`REBUJI_IMAP_HOST`、`REBUJI_IMAP_PORT`、`REBUJI_IMAP_ENCRYPTION`、`REBUJI_IMAP_USERNAME`、`REBUJI_IMAP_PASSWORD`
  - 名前に `_FILE` を付けて、値をファイルから読む書き方も、Docker と同じように読む（`Environment::get()` と同じ決まり）
- 読まない名前：`REBUJI_VERSION`、`REBUJI_DOMAIN`、`REBUJI_MAIL_CA_FILE`、`REBUJI_HTTPS`、`REBUJI_TRUSTED_PROXIES`。あれば「使いません」と 1 行出して続ける。ほかの `REBUJI_` で始まる知らない名前も同じ（打ち間違いに気づけるように）。**[判断]** Docker の `.env` をそのまま渡せる。`REBUJI_MAIL_CA_FILE` は、レンタルサーバー版には CA を足す設定が無いので使えない
- **ファイルが先、無ければ聞く。** パスワードを書かなかったファイルなら、パスワードだけを聞く。**[判断]** パスワードを書かないファイルを、おすすめとして文書に書く
- **ファイルは設置のときに一度だけ読む。** 値は、画面の初期設定と同じく、`storage/config.php`（DB）と `settings` テーブル（メール）に入る。後から変えるのは設定の画面で、Docker のように画面で変えられなくなることはない。**[判断]** レンタルサーバー版には環境変数が無く、設定の画面が変える場所。文書にもこの違いを書く
- 管理者のパスワードは、ファイルからは読まない（Docker と同じ）。管理者の名前とメールアドレスも、Docker に名前が無いので聞く。**[判断]**
- しきい値と 1 時間の上限は聞かず、既定（震度5弱、100 通）で始め、終わりに「設定の画面で変えられます」と出す。**[判断]** Docker でもこの 2 つは画面で決める。100 通は、元の設計 2.1 の表のどのプランの上限も超えない
- パスワードを含むファイルが、ほかの利用者に読める権限なら、注意を出す（止めない）。終わりに「パスワードを書いたなら、ファイルを消してください」と出す。**[判断]**

### 3.4 置き方

- **`--public` を渡したとき**：本体は `--root` に置き、`public/` の中身（`index.php`、`.htaccess`、`assets/`）を `--public` に写し、その隣に `--root` を返す `rebuji-root.php` を作る。今の文書の「本体を公開ディレクトリの外に置く」置き方と同じ形。`--public` は、置いたときに `upgrade.public_dir` として覚える（`bin/upgrade.sh` が読む。流し直しで `--public` を忘れても、黙って全体を置く形に変わらない）。**[判断]** SSH があるなら、本体を外に置けるので、こちらが安全
- **`--public` を渡さないとき**：パッケージ全体を `--root` に置く。`--root` が公開ディレクトリの中にあり、`--url` がその場所を指す形（今の文書の「全体を公開ディレクトリに置く」置き方）。同梱の `.htaccess` が守り、公開の確かめ（3.6 の 6）が、守れていることを確かめる。**[判断]** SSH があっても本体を外に置けないサーバー（ホームが公開ディレクトリになっているもの）でも使える。`--root` が公開されていなければ、URL がこの Re:無事 に届かないので、確かめで止まる
- `--public` は、まだ無いか空のディレクトリでなければ止まる。ただし、前の回がこの `--root` のために置いたもの（`rebuji-root.php` が `--root` を指している）なら、置き直す（3.7）。止まるときは、見つけたファイルを並べる。この確かめは、zip を取る前にする。**[判断]** ほかのサイトのファイルを上書きしない。サーバーによっては、新しい公開ディレクトリに仮の `index.html` を置くので、何があるかを見せる
- `--root` は、まだ無いか空のディレクトリ、または設置を終えていない Re:無事（3.7）でなければ止まる。設置を終えた Re:無事 なら、`bin/upgrade.sh` を案内して止まる。**[判断]**
- `--root` と `--public` が同じ、または一方がもう一方の中にあるときは止まる。
- `--root` は、全部そろってから現れる。zip は `--root` の隣の一時的なディレクトリに展開し、名前を変えて `--root` にする。途中で止まっても、半分だけの `--root` が残らない。**[判断]**

### 3.5 php を探す

- 順に：環境変数 `PHP`、`PATH` の `php`（8.3 以上なら）、サーバーが版ごとに置く場所（さくらのレンタルサーバの `/usr/local/php/<版>/bin/php` など）のうち、8.3 以上でいちばん新しいもの。コマンドラインの php（`PHP_SAPI === 'cli'`）であること。使う php を 1 行で示す。**[判断]** さくらでは、`PATH` の `php` が画面の PHP より古いことがある（今の文書の cron の注意と同じ）
- さくら以外の版ごとの場所は、builder が各社の公式の文書で確かめて足す（7 章）。
- 見つけた php を、cron の行にも使う。
- ウェブの PHP は、サーバーの管理画面で決まり、コマンドラインと違うことがある。これは公開の確かめ（3.6 の 6）で分かる（古ければ、`index.php` が 500 で理由を返す）。そのときは「サーバーの管理画面で、ウェブの PHP を 8.3 以上にしてください」と出して止まる。

### 3.6 順番と、各段で確かめること

`installed_at` を書くのは 11 だけ。それまでは「設置を終えていない」。

1. **道具**：php（3.5）、`unzip`、`curl`。無ければ理由を出して止まる。
2. **zip を取る**：`bin/upgrade.sh` と同じ確かめ（GitHub の API、zip の URL の形、GitHub が示す sha256 と比べる）。`--zip` なら sha256 を示すだけ（`bin/upgrade.sh` と同じ）。
3. **展開して置く**（3.4）。ファイルの権限は zip のまま（`bin/upgrade.sh` と同じく `umask 022`）。
4. **URL**：`--url` か、聞く。`http://` なら、ログインが暗号化されないことを注意する（止めない。画面の初期設定と同じ）。
5. **DB**：ファイルの `REBUJI_DB_DRIVER` が `mysql` なら MySQL、それ以外は SQLite。MySQL の値で足りないものは聞く。つないで、テーブルを作り、`storage/config.php` に書く（画面の「データベース」と同じ。失敗の理由からパスワードを伏せるのも同じ）。
6. **公開されていないことの確かめ**：画面の「公開されていないことの確認」と同じ `ExposureCheck` を使う（手がかりのファイルで、URL がこの Re:無事 に届くことを確かめてから、データベースや設定の URL が 403 か 404 になることを確かめる）。
   - **[判断] 手がかりが、ウェブ側の様子も返す。** 画面の初期設定では、その画面が開けていること自体が「URL が正しい」「ウェブの PHP がアプリを動かせる」の証拠になり、`PackagePath` もそのリクエストから分かる。コマンドラインでは、手がかりへのリクエストが唯一の証拠になる。そこで、手がかりに答えるとき、ウェブ側は次のことも返す：
     - 本体の URL のパス（`PackagePath` と同じ決め方。本体が文書ルートの外なら「無い」）
     - 選んだ DB の PDO の拡張があるか、`storage/` に書けるか（画面の「環境の確認」が見ているもの）
   - 本体が公開ディレクトリの中にあるなら、その URL でも確かめる。**[判断]** `--public` を渡しても、`--root` が別の公開ディレクトリの中にあれば、本体のファイルに URL がある。そこを確かめずに通すと、画面の初期設定より弱くなる
   - **[判断] 手がかりが「この Re:無事」でない答えを返したら（404、403、500、ほかの中身など）、理由を出して止まる。** 「ブラウザで確かめた」で通すことはできない。URL が違う、本体が公開されていない、ウェブの PHP が古い、`.htaccess` が効かない、ウェブがほかの利用者で動いていて `storage/` を読めない、のどれでも、cron とメールは動くのに、最後に出すログインと見張りの URL が使えないまま設置を終えてしまうため。転送（たとえば `https://` へ）なら、転送先の URL を示して、それで流し直すよう出す。
   - **サーバーから自分の URL に接続できないとき**（接続そのものの失敗）だけ、ブラウザに手伝ってもらう：
     1. 手がかりの URL を示し、「ブラウザで開いてください」と出して待つ。ウェブ側は、開かれたことと、上のウェブ側の様子を `storage/` に書く。スクリプトはそれを読んで先へ進む。これで、URL が正しいこと、ウェブの PHP が動くこと、本体の URL が分かる
     2. そのうえで、画面の初期設定と同じく、確かめる URL（本体のファイルの URL を含む）を並べ、「ブラウザで開いて、どれも 403 か 404 になりましたか？ [y/N]」と聞く
     - **[判断]** 画面の初期設定と同じ強さにそろえる。画面の初期設定でも、自分の URL に接続できないサーバーでは、ファイルの確かめを人に頼んでいる
   - 手がかりと、ブラウザで開かれたことの記録は、設置を終える前だけ答える（今の `/install/probe/…` と同じく、`InstalledGate` が設置後は閉じる）。画面の初期設定が使う手がかりの動きは変えない。
7. **最初の管理者**：画面の「最初の管理者」と同じ決まり（`AdminStep::validate()`）。管理者がもういれば、名前を示して飛ばす（3.7）。
8. **メール**：画面の「メールの設定」と同じく、値を確かめて（`SettingsForm::validate()`）保存し、`imap.since` を書き、メールボックスにログインし、最初の管理者にテストメールを送る。失敗したら理由を出し、メールの設定を聞き直す（ファイルの値が原因なら、ファイルを直すよう出して止まる）。
9. **cron の問い**（3.8）：何分ごとか、設置を終えたら足してよいか。ここではまだ書かない。
10. **返信**：`bin/console check --wait-reply` と同じ見つけ方（`SetupReplyFinder`）で、5 分まで待つ。来なければ「もう少し待ちますか？ [Y/n]」。これが最後の問い。
11. **仕上げ**：`status.token` と `installed_at` を書き、`storage/install-key.txt` があれば消す（画面の「仕上げ」と同じ）。
12. **cron を書く**：9 で `y` なら、聞き直さずに足す（3.8）。
13. 見張りの URL、ログインの URL、しきい値と上限の既定を出す。

### 3.7 途中で止まったとき

- **同じコマンドをもう一度流す**と、続きから進む。決まった進み具合のファイルは作らず、各段が「今どうなっているか」を見て決める。**[判断]** 状態を二重に持たない
  - 展開と配置：`--root` に設置を終えていない Re:無事 があれば、それを使う（新しい版が出ていても、取り直さない）。`--public` が前の回のものなら置き直す。`--public` を渡し忘れても、前の回が覚えた公開ディレクトリ（3.4）を使う。
  - DB：つなぎ直して、テーブルを作る（済んでいれば何もしない）。ファイルの値が、前の回に保存した値より先。
  - 管理者：もういれば飛ばす。
  - メール、返信、公開の確かめ：毎回やり直す。設置を終える前の関門なので、前の回の結果は信じない。
- 設置を終える前は、今と同じく、その URL で画面の初期設定も開ける（設置の鍵が要る）。どちらで終えてもよい。
- いつ Ctrl-C を押してもよい。半分だけの `--root` は残らず（3.4）、`storage/config.php` は書き換えが途中で見えない（`ConfigFile::save()`）。

### 3.8 cron

- 問いは返信を待つ前（3.6 の 9）、書くのは設置を終えた後（3.6 の 12）。**[判断]** 3.1 の「人が答える問いは、返信を待つ前に全部済ませる」のため。設置を終える前に書くと、cron がまだ設置していないアプリを動かしてしまう
- `crontab` が使えるなら、何分ごとかを聞き（既定 5。1 分ごとにできるサーバーなら 1 をすすめる。今の文書と同じ）、足す行を示して「設置を終えたら足しますか？ [y/N]」と聞く。`y` なら、設置を終えた後に、今の行をそのまま残して 1 行足す。`<root>/bin/cron.php` を含む行がもうあれば足さず、そう示す。**[判断]**
- `crontab` が無い、書けない、または `N` なら、サーバーの管理画面に登録する php と `bin/cron.php` の場所、間隔を出す。設置はそれでも終わっている。
- 何分ごとにできるかはサーバーで違い、スクリプトには分からない。既定を 5 にするのは、元の設計 2.1 の表のどのプランでも登録できるため。**[判断]**
- **SSH で `crontab` を書いてよいかは、サーバーで違う。** 管理画面だけで cron を扱い、`crontab` の書き換えを認めない、または管理画面で編集すると書き換わるサーバーがありうる。builder が 4 社の公式の文書で確かめ、結果を `docs/install.md` にサーバーごとに書く（認めないサーバーでは `N` と答え、管理画面に登録する）。足した行が消えても、見張りの URL が 15 分で 503 を返すので気づける。足したあとの表示でも、そのことを 1 行で伝える。**[判断]**

## 4. 作りの形 **[判断]**

`bin/upgrade.sh` と `bin/console upgrade:install` の分け方にそろえる。

- **`bin/install.sh`（sh）**：引数を読む、php を探す、zip を取って確かめる、展開して `--root` にする、そのあと `"$php" "$root/bin/console" install …` に引き渡す。FreeBSD の sh と Linux の dash で動く（`bin/upgrade.sh` と同じ）。引き渡すのは場所、URL、ファイルのパス、引数だけで、秘密は渡さない。
  - **`install.sh` から `bin/console install` に渡す引数の形は、一度決めたら変えない。** **[判断]** いつも最新のリリースの `install.sh` が取られるので、`--version` で選んだ前の版の `bin/console install` とも話が通じる必要がある
- **`bin/console install`（PHP）**：3.4 の配置から 3.8 までの残り全部。
  - 画面の各段と、確かめと書き込みを共有する。写して二つにしない。共有のしかた（各段のうち HTTP に関わらない部分を別のクラスに出す、など）は builder に任せる。
  - Docker（`REBUJI_ENV_CONFIG=1`）では止まる。設置を終えた Re:無事 でも止まり、`bin/upgrade.sh` を案内する。
  - コンテナは設定ファイルを最初に読むことがあるので、DB を決めた後に作る部品が、決める前の設定を掴まないようにする。
- **ウェブ側**：手がかり（`ProbeController`）が、ウェブ側の様子（本体の URL のパス、PDO の拡張、`storage/` に書けるか）を返し、ブラウザで開かれたときはそれを `storage/` に書く（3.6 の 6）。画面の初期設定から使うときの動きは変えない。
- **リリース**：`bin/release.sh publish` が、zip に加えて `bin/install.sh` を `install.sh` という名前でリリースに上げ、zip と同じように、上げたもののハッシュを手元と比べる。こうすると、`https://github.com/shimomo/re-buji/releases/latest/download/install.sh` が、いつも最新のリリースのスクリプトになる。リリースのスキル（`.claude/skills/releasing-re-buji`）とリリースノートのひな形にも、`install.sh` を足す。
- `--version` で、`bin/console install` を持たない古い版を選んだら、zip を展開したところで止まる（`bin/upgrade.sh` が `UpgradeInstallCommand.php` の有無で止まるのと同じ）。
- 版を上げてリリースする。`install.sh` を最初に載せる版になる。番号は計画で決める。

## 6. 確かめ方 **[判断]**

- `bin/console install`：PHPUnit で、今の `UpgradeInstallCommandTest`・`CheckCommandTest` と同じく、メールと HTTP を偽物にして確かめる。少なくとも次のこと：
  - ファイルの値が先で、無い値だけを聞く。読まない名前と知らない名前で「使いません」と出す
  - 確かめ（公開、返信）が通るまで `installed_at` を書かない
  - 途中で止めて流し直すと続きから進み、管理者を二重に作らない
  - `--public` にほかのファイルがあれば止まる。前の回のものなら置き直す
  - `crontab` の行の追加：今の行を残す、二重に足さない、`N` なら書かない（`crontab` を呼ぶところは差し替えられるようにする）
  - 本体が公開ディレクトリの中にあり、そのファイルがウェブから読めるなら、止まる
  - 手がかりが「この Re:無事」でない答え（404、500、ほかの中身、転送）を返したら、`y` と答える道を出さずに止まる。接続できないときだけ、ブラウザで開かれた記録を待ち、そのあとで人に確かめを頼む
  - 手がかりが返すウェブ側の様子（本体の URL のパス、PDO の拡張、`storage/` に書けるか）。画面の初期設定から使うときは今と同じ答え
  - 人が答える問いは、返信を待つ前に終わる（返信を読めた後に `ask` を呼ばない）
- `bin/install.sh`：`ReleaseScriptTest` と同じく、PHPUnit からスクリプトを流して、止まるべきところ（設置を終えた `--root`、空でない `--root`、`--root` と `--public` の重なり、古い php）と、手元で作った zip を `--zip` で渡したときの展開を確かめる。GitHub から取るところは手で確かめる。
- 実際のレンタルサーバー（さくらのレンタルサーバ）で、最初から最後まで流すことを、リリースの前に作者に頼む。**[判断]** 公開の確かめ、php の場所、`crontab` は、サーバーごとの違いが出るところで、偽物では確かめきれない。
