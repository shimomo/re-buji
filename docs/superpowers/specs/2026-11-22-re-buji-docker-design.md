## 1. なぜ作るか

v0.2.3 までの設置は「zip を取る → FTP で置く → `storage/install-key.txt` を FTP で開いて貼る → ブラウザの初期設定 → cron を登録」である。作者が自分で設置してみて、**この手順をこなせるのはある程度の技術力がある人だ**と感じた。**[決定]** 「zip を置くだけで技術者でない人でも動く」という前提は、このシステム（SMTP・IMAP・cron・監視が要る）では無理がある。

そこで、主な相手を**技術者**に置き直し、技術者にとって簡単な入口を用意する。**[決定]**

### 成功とは

- 技術者が、リポジトリを clone して（またはイメージを取って）**コマンド 1 つ**で手元に Re:無事 を立ち上げ、本物のメールアカウントなしで「訓練の連絡を送る → 返信する → 責任者の画面に『無事』と出る」までを確かめられる。
- 同じ仕組みで、VPS にドメインを向けて `.env` を書けば、**HTTPS 付きで本番として動く**。

### 目標

- 手元で試せる Docker の構成を用意する。**[決定]**
- VPS などで本番稼働できる Docker の構成を用意する。**[決定]**
- Docker では、ブラウザの初期設定を通さずに設置を終えられる。**[決定]**
- 本番用の構成で、HTTPS の証明書の取得と更新まで面倒を見る。**[決定]**

### 目標にしないこと

- Docker とレンタルサーバー以外の動かし先（Docker を使わない VPS への直接設置、Fly.io などのコンテナ実行サービス、Kubernetes）。**[決定]** 今回はこの 2 つで十分。
- 今のレンタルサーバー版から Docker 版への引っ越し（データベース・設定・状態の URL の引き継ぎ）。**[決定]** 今回は新しく設置する場合だけを扱う。
- 複数台での冗長化や、1 台を超える規模への拡張。**[判断]** 元の設計と同じく、数十〜数百人の組織 1 つを 1 台で受け持つ。
- Docker 版だけの新機能。アプリの振る舞いはレンタルサーバー版と同じにする。**[判断]**

### やってはいけないこと（アンチゴール）

- **レンタルサーバー版を壊すこと。** **[決定]** zip の作り方、FTP での設置、ブラウザの初期設定、`.htaccess` による保護は今のまま動き続ける。Docker のための変更は、Docker で動いていると分かったときだけ効くようにする。
- **手元で試しているときに、本物の人へメールが出ること。** 手元の構成では、送ったメールはすべて同梱のテスト用メールサーバーに留まり、外へ出ない。
- 管理者のパスワードを `.env` や環境変数、イメージ、ログに残すこと。
- `storage/`（データベース、設定、ログ）がウェブから読めること。
- HTTPS なしで本番の管理画面を外に出す構成を、既定にすること。

## 2. 全体の形

リポジトリに次を足す。**[判断]**

```
docker/
  Dockerfile            アプリのイメージ（ウェブ・cron 共通）
  entrypoint.sh         起動時の準備（マイグレーションなど、6 章）
  Caddyfile             FrankenPHP（Caddy）の設定
compose.yaml            本番用（VPS）
compose.dev.yaml        手元で試すための上書き（テスト用メールサーバーとウェブメール）
.env.example            本番用の環境変数の見本と説明
docs/docker.md          Docker での設置・更新・バックアップの手順
```

### 2.1 アプリのイメージ **[判断]**

- **FrankenPHP**（公式イメージ、PHP 8.3 以上）を土台にする。Caddy が組み込まれているので、1 つのイメージで PHP を動かし、HTTPS の証明書（Let's Encrypt）の取得と更新もできる。nginx＋php-fpm＋別の Caddy の 3 つを組むより、技術者が見るものが少ない。
- 公開するのは `public/` だけ（ドキュメントルート）。`storage/`・`src/`・`vendor/` はドキュメントルートの外にあるので、ウェブから読めない。
- `vendor/` はイメージを作るときに `composer install --no-dev --optimize-autoloader` で入れる。
- 必要な拡張：`pdo_sqlite`、`pdo_mysql`、`mbstring`（と、アプリが今使っているもの。builder が `composer.json` と環境の確認の段階から洗い出す）。
- 動かすユーザーは root でないもの。`storage/` はボリュームにし、そのユーザーが書けるようにする。
- イメージは GitHub のリリースのたびに `ghcr.io/shimomo/re-buji:<版>` と `:latest` で配る。リポジトリを clone して `docker compose build` でも作れる。

### 2.2 サービスの分け方 **[判断]**

| サービス | 役目 | 本番 | 手元 |
|---|---|---|---|
| `app` | ウェブ（FrankenPHP） | ○ | ○ |
| `cron` | `bin/cron.php` を 1 分ごとに動かす | ○ | ○ |
| `mail` | テスト用のメールサーバー（SMTP と IMAP） | × | ○ |
| `webmail` | テスト用のウェブメール（返信するため） | × | ○ |

- `app` と `cron` は同じイメージで、同じ `storage/` のボリュームを使う。
- `cron` は 1 分ごと。**[判断]** レンタルサーバーの「5 分ごと」の制約が無いので、元の設計で勧めている 1 分ごとにする。前の回が終わっていなければ重ねて動かさない（今の `bin/cron.php` に重ならない仕組みがあるならそれに任せる。無ければ builder が確かめて足す）。
- 本番の既定はデータベースに SQLite を使う（`storage/` の中）。MySQL を使いたい人は `.env` で指定でき、MySQL のサーバーは自分で用意する（Compose に MySQL は同梱しない）。**[判断]** 1 台・数百人までなら SQLite で足り、バックアップもファイル 1 つで済む。

## 3. 手元で試す

```bash
docker compose -f compose.yaml -f compose.dev.yaml up -d
docker compose exec app php bin/console admin:create
```

で、`http://localhost:8080` に Re:無事、`http://localhost:8081` にウェブメールが立ち上がる（番号は [判断]）。

- `compose.dev.yaml` は、`app` の HTTPS を切って `http://localhost:8080` で出し、メールの設定を同梱のテスト用メールサーバーに向ける。
- テスト用メールサーバーは、SMTP と IMAP の両方を持ち、**宛先にかかわらず外へは出さず**、自分の中のメールボックスに配るものを使う（例：GreenMail）。ウェブメールはそのメールボックスを開いて返信できるもの（例：Roundcube）。どの製品を使うかは builder に任せるが、「外へ出さない」は必ず守る。**[判断]**
- Re:無事 は送信・受信とも TLS の上でしかログインしない（元の設計）。テスト用メールサーバーは自己署名の証明書で TLS を話し、手元の構成だけがその証明書を信頼する設定を `app` と `cron` に渡す（7 章の `REBUJI_MAIL_CA_FILE`）。**TLS を切る抜け道は作らない。** **[判断]**
- テスト用の従業員（例：`taro@example.test`、`hanako@example.test`）のメールボックスを用意しておき、ウェブメールでその人として返信できるようにする。従業員そのものは管理画面か CSV で登録する（見本の CSV を `docker/dev/employees.csv` に置く）。**[判断]**
- 手元の流れ（`docs/docker.md` に書く）：起動 → 管理者を作る → ログイン → 見本の CSV を取り込む → 「訓練」で連絡を送る → ウェブメールで返信する → 1 分ほど待つ → 責任者の画面で「無事」になる。
- 気象庁のフィードは、手元でも本物を読みに行く（訓練・試験の電文では送らないのは元の設計どおり）。手元で本物の地震で連絡が出ても、メールは外へ出ないので害はない。

## 4. VPS で本番として動かす

```bash
cp .env.example .env    # ドメインとメールの設定を書く
docker compose up -d
docker compose exec app php bin/console admin:create
docker compose exec app php bin/console check
```

### 4.1 HTTPS **[決定]（面倒を見る）／方式は [判断]**

- `.env` の `REBUJI_DOMAIN` にドメインを書くと、`app`（FrankenPHP の Caddy）が Let's Encrypt の証明書を自動で取り、更新する。VPS は 80 番と 443 番を開ける。
- 証明書などの Caddy のデータは、`storage/` とは別のボリュームに置く。
- すでに nginx などのリバースプロキシを持っている人のために、HTTPS を切って `127.0.0.1:8080` だけで待ち受ける出し方も選べるようにする（`.env` の 1 項目か Compose の profile で切り替える。どちらにするかは builder に任せる）。このときは、プロキシからの `X-Forwarded-Proto` を信じる相手を設定で限る。
- 公開する URL（メール本文や状態の URL に使う）は `REBUJI_BASE_URL` で渡す。HTTPS を自分で面倒見る形では `https://<REBUJI_DOMAIN>` を既定にする。

### 4.2 更新

```bash
docker compose pull
docker compose up -d
```

- 起動時にマイグレーションを自動で流す（6 章）。
- `.env.example` では版を固定したタグ（`re-buji:0.3.0` のような）を勧め、`latest` は書かない。**[判断]** 安否確認は止まると困るので、知らないうちに版が上がらないようにする。

### 4.3 バックアップ

- `storage/` のボリュームを丸ごと写せば足りる（SQLite のとき）。`docs/docker.md` に、止めずに取る方法（`sqlite3 .backup` か、`bin/console backup` のようなコマンド。どちらかは builder に任せる）と、戻し方を書く。

## 5. 初期設定をブラウザから外す **[決定]**

Docker で動いているときは、ブラウザの初期設定を使わない。

### 5.1 Docker で動いていることの見分け **[判断]**

- 環境変数 `REBUJI_ENV_CONFIG=1`（イメージに入れておく）があるときを「環境変数で設定する形」とする。これが無ければ、今のレンタルサーバー版とまったく同じに動く。
- この形では、データベースの接続や公開する URL など、技術者が設置のときに決めるものを環境変数から読む（7 章）。
- `storage/config.php` は残し、**アプリが自分で作って書き換える実行時の値だけ**を置く（`installed_at`、`status.token` など）。**[判断]** 今これらは `InstalledGate`・`bin/cron.php`・`HomeController`・`StatusController`・`StatusTokenController` が `config.php` を読み書きしている。置き場所を変えると、レンタルサーバー版の通り道にも手が入るため。環境変数で決まる項目は、`config.php` に値があっても環境変数を使う（設定を読むところで、環境変数を上に重ねる）。
- 初期設定の画面（`/install`）は開けない（404 か、「この設置では使いません」と出す）。設置の鍵（`install-key.txt`）も作らない。**[判断]** コンテナを動かせる人は、すでに設置の権限を持っている。

### 5.2 今の初期設定の各段階をどこへ移すか

| 今の段階 | Docker では |
|---|---|
| 環境の確認 | イメージを作るときに決まる。起動時の `bin/console check` でも確かめる |
| 設置の鍵 | 要らない |
| データベース | 環境変数。起動時にマイグレーションを流す |
| 最初の管理者 | `bin/console admin:create`（5.3） |
| メールの設定 | 環境変数（7 章）。管理画面の「設定」でも見られる（5.4） |
| 返信の確認 | `bin/console check` で確かめる（5.5） |
| 公開されていないことの確認 | 要らない（`public/` だけがドキュメントルート） |
| 仕上げ（cron と見張りの URL） | cron は `cron` サービスが動かす。見張りの URL は管理画面のホームに出る（今と同じ）。`bin/console status-url` でも出す |

「初期設定が終わった」（今の `installed_at`）に当たる印は、最初の起動でマイグレーションを流し終えたときに付ける。**[判断]** 管理者がまだいないあいだは、ログイン画面に「`bin/console admin:create` で管理者を作ってください」と出す。

### 5.3 最初の管理者 **[判断]**

- `bin/console admin:create` が、名前・メールアドレスを引数か対話で受け取り、パスワードは対話で 2 回入れる（画面に出さない）。12 文字以上などの決まりは、今の管理者の作成と同じものを使う。
- パスワードを引数や環境変数で受け取る口は作らない（シェルの履歴やログに残るため）。対話できないとき（CI など）のために、標準入力から 1 行読む口だけは用意する。
- 2 人目からは、今と同じく管理画面で作る。

### 5.4 環境変数と管理画面の「設定」がぶつかったとき **[判断]**

- 環境変数で渡した項目は、管理画面の「設定」では**変えられない**（入力欄を読み取りだけにし、「環境変数 `REBUJI_SMTP_HOST` で決まっています」と添える）。パスワードは画面に出さない。
- 環境変数で渡していない項目は、今までどおり画面で変えられ、データベースに入る。
- 理由：環境変数とデータベースの両方に値があって片方が黙って勝つと、「画面で直したのに効かない」「再起動したら戻った」が起き、地震のときに気づく。どちらで決まっているかを画面で見えるようにする。

### 5.5 確かめるコマンド

`bin/console check` は、今の初期設定の「メールの設定」と「返信の確認」で確かめていることを、コマンドで行う。

1. データベースにつながり、マイグレーションが最新か。
2. `storage/` に書けるか。
3. IMAP にログインできるか。
4. 最初の管理者（か、引数で指定したアドレス）にテストメールを送る。
5. （`--wait-reply` を付けたとき）そのテストメールへの返信を待ち、読めたら成功。

- 結果は 1 行ずつ「✓／✕ と理由」で出し、1 つでも失敗すれば終了コードを 0 以外にする。
- 失敗しても `app` と `cron` の起動は止めない。メールの問題は、今と同じくホーム画面の「確かめてほしいこと」に出る。**[判断]** 起動を止めると、メールの一時的な不調で画面まで見られなくなる。
- 返信を読む基準の時刻（今の `imap.since`）は、最初の起動のときに付ける。
- `.env` で IMAP の接続先かユーザー名を変えて起動し直したときは、今の管理画面（`SettingsController`）と同じく `imap.since` を今の時刻に付け直す。**[判断]** 付け直さないと、新しいメールボックスにある古いメールまで照合してしまう。起動のたびに、前に使った接続先とユーザー名を `SystemState` に覚えておき、比べる（6 章の 4）。

## 6. 起動時の準備（entrypoint）**[判断]**

`app` が起動するたびに、次を順に行う。

1. 必要な環境変数がそろっているかを確かめる（足りなければ、何が足りないかを日本語で出して止める）。
2. `storage/` の中の必要なディレクトリを作り、権限を整える。
3. マイグレーションを流す（新しい版に上げたときも、ここで流れる）。
4. 初回なら「初期設定が終わった」の印と状態の URL の文字列を `storage/config.php` に、`imap.since` をデータベースに作る。初回でなくても、IMAP の接続先かユーザー名が前回と違えば `imap.since` を付け直す（5.5）。
5. ウェブを起動する。

- `cron` は 3〜4 をしない（`app` に任せる）。`app` の準備が終わる前に動いた回は、何もせずに終わる（今の `bin/cron.php` の「初期設定が終わるまで何もしない」を流用する）。
- マイグレーションを 2 つのコンテナが同時に流さないよう、流すのは `app` だけにする。

## 7. 環境変数 **[判断]**

名前はすべて `REBUJI_` で始める。`.env.example` に、項目ごとの説明と既定値を日本語で書く。

| 環境変数 | 意味 | 既定 |
|---|---|---|
| `REBUJI_DOMAIN` | HTTPS を自動で取るドメイン | （必須。HTTPS を自分で面倒見るとき） |
| `REBUJI_BASE_URL` | 公開する URL | `https://<REBUJI_DOMAIN>` |
| `REBUJI_DB_DRIVER` | `sqlite` か `mysql` | `sqlite` |
| `REBUJI_DB_HOST` ほか | MySQL のときの接続先 | |
| `REBUJI_SMTP_HOST`・`_PORT`・`_ENCRYPTION`・`_USERNAME`・`_PASSWORD` | 送信 | 今の設定の既定 |
| `REBUJI_MAIL_FROM_ADDRESS`・`_FROM_NAME` | 送信元 | |
| `REBUJI_IMAP_HOST`・`_PORT`・`_ENCRYPTION`・`_USERNAME`・`_PASSWORD` | 受信 | 今の設定の既定 |
| `REBUJI_MAIL_CA_FILE` | メールサーバーの証明書を確かめるときに追加で信頼する CA（手元のテスト用） | 空 |
| `REBUJI_TIMEZONE` | タイムゾーン | `Asia/Tokyo` |

- しきい値・再送の回数・1 時間の上限・メールの文面などは、環境変数では渡さず、今までどおり管理画面で決める。**[判断]** 地震のたびに責任者が見直す値で、技術者でない管理者も変える。
- パスワードの類は、`_FILE` を付けた名前（`REBUJI_SMTP_PASSWORD_FILE`）で Docker secrets のファイルからも読めるようにする。**[判断]**
- 7 章の表は目安。今の `storage/config.php` と `settings` テーブルにある項目を builder が洗い出し、「技術者が設置のときに決めるもの」は環境変数に、「管理者が運用で変えるもの」は画面に、の線で振り分ける。

## 8. レンタルサーバー版との関係 **[決定]（捨てない）**

- zip の作り方（`bin/build-release.sh`）と中身は変えない。`docker/`・`compose*.yaml`・`.env.example` は zip に入れない。
- `bin/console` はレンタルサーバー版の zip にも入ってよいが、SSH が無い人には使えないので、README の手順には出さない。
- README の冒頭の「設置」を、「Docker で動かす（技術者向け、おすすめ）」と「レンタルサーバーに置く」の 2 つに分ける。Docker の詳しい手順は `docs/docker.md` へ。
- 元の設計の「レンタルサーバーに置ける」という説明は残しつつ、主な相手が技術者であることが README から分かるようにする。

## 9. リリース **[判断]**

- 版は v0.3.0 とする。
- `bin/release.sh publish` のあと、タグを受けて GitHub Actions がイメージを作り、`ghcr.io` に `:<版>` と `:latest` で上げる（amd64 と arm64）。イメージ作りはタグを打ったコミットから行い、zip と同じコミットになるようにする。
- リリースのスキル（`.claude/skills/releasing-re-buji`）に、イメージが上がったことを確かめる手順を足す。
- CI に、手元の構成（テスト用メールサーバーつき）でイメージを作って起動し、`bin/console check --wait-reply` が通ることを確かめるジョブを足す。テストメールへの返信は、CI のスクリプトがテスト用メールサーバーの SMTP から送る（`In-Reply-To` を付けた空の返信）。**[判断]** 送って読めるまでを通しで確かめないと、Docker 版で一番壊れやすい「返信を読む」ところが守られないため。

## 10. builder に任せること

- テスト用メールサーバーとウェブメールの製品選び（3 章の条件を満たすもの）。
- HTTPS を切る形の切り替え方（`.env` の項目か Compose の profile か）。
