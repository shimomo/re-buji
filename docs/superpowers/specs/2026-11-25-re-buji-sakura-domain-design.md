## 1. なぜ直すか

作者が、main（`dce1197`）から作った 0.4.0 の zip（sha256 `73953cdc…`）を、さくらのレンタルサーバで流した。php の検出（`/usr/local/bin/php` 8.3.37）、展開、公開ファイルの配置、SQLite の作成は、最初から通った。詰まったのは、公開する URL と、返信の待ちだった。

**公開する URL（初期ドメインで試したとき）。** 3 回とも、URL を聞くところで止まった。

1. `https://shimomo.sakura.ne.jp/re-buji/` を入れた → 404。公開ディレクトリ（`~/www/anpi-test`）とは別の場所で、本番の 0.3.9 が答えていた。
2. `https://shimomo.sakura.ne.jp/re-buji-test/` を入れた → サイトの設定がパスを捨てて `https://shimomo.net/?from=console` に転送した。インストーラは「`--url https://shimomo.net/?from=console` を付けて、もう一度流して」と案内した。
3. 案内どおりに打つと、さくらの既定のシェル（tcsh）が `?` をファイル名のパターンとして読み、「照合パターンに合いません」で止まった。

2 と 3 はインストーラの誤り：確かめのために付けた `?from=console` を案内に残した。Re:無事 ではない転送先（パスが捨てられている）を案内した。URL を引用符で囲まなかった。1 と 2 は、質問がどのディレクトリの URL かを示さず、届かないと流し直しになることが重なった。

**返信の待ち（独自ドメインで流し直したとき）。** 作者は 0.3.9 を消し、サブドメイン `re-buji.shimomo.net`（ドキュメントルート `~/www/re-buji/`）を作って流し直した。URL の確かめ、管理者、メールの設定、cron の登録は通り、設置を終えた。途中で次のことがあった。

4. 受信のログインが、1 回目だけ「NO Login failed.」で断られた。同じ設定（パスワードは貼り付け）で流し直すと通った。インストーラは 1 回目も 2 回目も同じ値を送る作りで、原因はこちらからは分からない。
5. 02:14 に返信したのに、待ちが見つけなかった。理由は 2 つ重なっていた。
   - 返信がメールソフトで既読になっていた。管理者のアドレスと、返信を受ける受信箱が、同じ `re-buji@shimomo.net` だった。待ちは未読のメールしか探さない。
   - 待ちは、5 分のあいだ 1 本の接続のまま探し続ける。さくらの受信サーバーは Courier-IMAP（接続したときの名乗り）で、同じ接続のままでは、新しく届いたメールが見えなかったと考えられる。
   作者が返信を未読に戻し、待ちが接続を張り直した回で見つかった。
6. 2 回目からの待ちは何も表示しないので、固まったように見えた。
7. テストメールの本文が「初期設定の画面で『返信を確かめる』を押してください」と、ブラウザで設置するとき向けのままだった。

作者の考え：
- **初期ドメイン（`アカウント名.sakura.ne.jp`）は、できれば避けたい。** 独自ドメインかそのサブドメインで使う。**[決定]**
- **独自ドメインには、案 A で応える**（2 章）。**[決定]**
- **いったん、さくらのレンタルサーバだけを対象にする。** ほかのサーバーを試す環境がない。**[決定]**

### 目標

- 手順書が、さくらの管理画面でドメインを用意するところから始まり、そのディレクトリと URL を `install.sh` に渡す形になる。
- URL を聞くときに、どのディレクトリの URL かを示す。手で入れた URL が届かなければ、その場で聞き直す。
- 転送を正しく扱う。同じディレクトリへの転送（http から https など）は、転送先を使って続ける。それ以外の転送は「届かなかった」として、転送先を示す。どちらでも `?from=console` を見せない。
- 返信の待ちが、既読になった返信も、待っているあいだに届いた返信も見つける。待っているあいだは、待っていることが分かる。

### 目標にしないこと

- ドメインのつなぎ先（公開フォルダ）を、インストーラが探したり、サーバーごとの決まりから決めたりすること（案 B、案 C）。
- さくら以外のサーバーで確かめること、その手順を書くこと。
- ブラウザの初期設定の、公開の確かめ（`ExposureStep`）を変えること。ブラウザは開いた URL を知っているので、URL の問題は起きない。
- 4 の、1 回目だけ受信のログインが断られたこと。同じ値を送っていて、手がかりがない。また起きたら、断られたその場でさくらのウェブメールに同じパスワードでログインして、どちらの側かを見分ける。
- パスワードの前後の空白を削る振る舞い（`SettingsForm::read` の `trim`）。前からあり、画面の設定も同じ。後回しの minor として扱う。

## 2. 案

- **A：管理画面でドメインを先に用意してもらい、インストーラはそのフォルダと URL を受け取る。**（採用 **[決定]**）
  インストーラが知る必要があるのは、ウェブが公開するディレクトリと、そこに届く URL の 2 つだけ。独自ドメインでも、組み合わせが違うだけ。どのドメインをどのフォルダにつなぐかは、人が管理画面で決める。
- **B：URL だけを聞き、ディレクトリはインストーラが探す。** 候補のフォルダに目印を置いて、どれが届くかで見つける。入力は減るが、ほかのサイトのフォルダにも書き、サーバーごとの候補の一覧を持つことになる。
- **C：`--host sakura` のように、サーバーごとのフォルダの決まりを組み込む。** サーバーごとに公式の資料で裏を取り、変わるたびに直すことになる。

A を選べる裏付け：Re:無事 は自分のドメインを覚えていない。画面のリンクはどれもそのとき開いている URL から作り（`src/Http/Url.php`、`src/Http/BasePath.php`。0.3.9 も同じ）、送るメールに URL は入らない。設置のときの URL は、届くか、守れているかの確かめにしか使わない。実際、作者の 0.3.9 は、設定を変えずに新しいサブドメインでも開いた。

## 3. 変えること

### 3.1 URL の質問 **[判断]**

- 質問にディレクトリを出す。`--public` があればそのディレクトリ、無ければ `--root`。例も添える。

  ```
  /home/shimomo/www/anpi を開く URL（例：https://anpi.example.jp）：
  ```

  理由：1 と 2 は、入れた URL が別のディレクトリを指していた。質問の場でディレクトリが見えれば、取り違えに気づける。
- **手で入れた URL が届かないときは、その場で聞き直す。** 入れ直しの数え方は、今の形式の誤りと同じ `TRIES`（3）を使い、通らなければ `GAVE_UP` で止まる。理由：手で入れたなら人がそこにいるので、流し直しより早い。
- **`--url` で渡した URL が届かないときは、今のとおり止まる。** 理由：渡した値を勝手に聞き直すと、設定ファイルや控えた手順と違う URL で入ってしまう。
- 公開する URL の確かめ（`reach`）は、URL を聞いた直後にする。ウェブの PHP の向き不向き（`pdo_<driver>` があるか）は、データベースを決めたあとに、今のとおり確かめる。理由：聞き直しは URL の質問のすぐあとでないと、間にデータベースの問いが挟まる。`InstallContext` は、確かめが通った URL で作る。

### 3.2 転送の扱い **[判断]**

`reach` の答えが 301、302、303、307、308 のとき、`Location` に確かめの道（`/install/probe/<nonce>`）が残っているかで分ける。

- **残っている**（http から https、`www.` の付け外しなど）：同じディレクトリに別の URL で届いている。道より前を新しい URL として、「→ <新しい URL> に転送されたので、こちらを使います」と出し、その URL でもう一度確かめる。手で入れた URL でも `--url` でも同じ。もう一度の確かめでまた転送されたら、届かなかったとして扱う（転送が回り続けないように）。
  理由：さくらの「HTTPS転送設定」は http から https へ 302 で転送する（[ドメインリダイレクトを設定したい](https://help.sakura.ad.jp/domain/2150/)）。http で入れても続けられる。転送先の確かめが通れば、nonce で、この Re:無事 に届いたと分かる。
- **残っていない**：Re:無事 ではないところへ送られている。「<URL> は <転送先> に転送されました。<ディレクトリ> に届いていません」と出し、届かなかったときの扱い（3.1）に進む。転送先からは、確かめのために付けた `from=console` を除く。
- `--url` を付け直してもう一度流す、という案内は無くなる。インストーラが案内するコマンドに URL かパスを入れるときは、`'…'` で囲む。理由：さくらの既定のシェルは tcsh で、`?` や `*` をファイル名のパターンとして読む。

### 3.3 届かなかったときの文 **[判断]**

「URL が正しいか、その URL で公開ディレクトリが公開されているか」を、「その URL が <ディレクトリ> を開くか」に変える。ディレクトリの名前を出すことで、別の場所を指していると気づける。

### 3.4 返信の待ち **[判断]**

`SetupReplyFinder` を使う、`bin/console install` と `bin/console check --wait-reply` の両方を直す。

- **既読の返信も探す。** テストメールへの返信は、番号（件名の `#<番号>`）か Message-ID（`In-Reply-To`、`References`）で見分けられるので、既読かどうかで分けない。受信サーバーの検索で絞ってから取り出し、5 秒ごとに受信箱を全部取り出すことはしない。理由：5 の 1 つ目。管理者のアドレスと受信箱が同じでも、返信をメールソフトで開いても通る。
  - cron の返信の取り込み（未読を読む）は変えない。
- **探すたびに、同じ接続の中で新しいメールを確かめる。** 検索の前に NOOP を送る。RFC 3501（6.1.2）は、NOOP を新しいメールを確かめる定期の問い合わせに使えるとしている。理由：5 の 2 つ目。cron の取り込みは毎回つなぎ直すので、影響がない。
- **待ちの回ごとに、「テストメールに返信してください。返信を待っています（5 分まで）…」を出す。** 理由：6。
- **テストメールの本文を、どちらの設置にも合う文にする。** 「このメールに、そのまま返信してください（本文は空で構いません）。」は残し、画面のボタンの案内は、画面で設置しているときに限る書き方にする。理由：7。

### 3.5 文書 **[判断]**

手順書（`docs/install.md` の「SSH で入れる」）を、さくらのレンタルサーバの手順にする。

1. **管理画面でドメインを用意する。** 「ドメイン/SSL」の「ドメイン新規追加」で、独自ドメインかそのサブドメインを足す（[ドメインを追加したい](https://help.sakura.ad.jp/domain/2145/)）。ドキュメントルートは、`~/www` の下の新しい空のフォルダにする（作者の管理画面で、サブドメインを足すときに指定できた。4 章）。反映には数時間かかることがある（同じページ）。
2. **無料 SSL を有効にする。** 「ドメイン/SSL」→ 対象の「設定」→「SSL設定」で Let's Encrypt を使う（[無料SSLを設定したい](https://help.sakura.ad.jp/rs/2153/)）。発行は数十分から数時間（同じページ）。Let's Encrypt は独自ドメインが対象（同じページ）。http から https への転送は、任意で「HTTPS転送設定」をオンにする（[ドメインリダイレクトを設定したい](https://help.sakura.ad.jp/domain/2150/)）。
3. **ブラウザで `https://<ドメイン>/` が証明書の警告なしに開くのを確かめてから、流す。**

   ```bash
   sh install.sh --public ~/www/anpi --url https://anpi.example.jp
   ```

- 手順書の冒頭に、「さくらのレンタルサーバ（スタンダードプラン以上。SSH と CRON がスタンダード以上のため）で確かめています。ほかのサーバーでは確かめていません」と書く。
- **返信を受けるアドレスについて一言書く。** テストメールの宛先（最初の管理者のアドレス）は、返信を受ける受信箱と別のアドレスがよい。同じでも通るが、受信箱のメールをメールソフトで読むと、Re:無事 が読むメールと混ざる。
- php の探し方の節：さくらのコマンドラインの php は `/usr/local/bin/php`（[プログラムのパス](https://help.sakura.ad.jp/rs/2252/)）。`install.sh` が探すほかの候補（`/usr/local/php/<版>/bin/php` など）のコードは残すが、手順書の例はさくらの形にする。理由：候補はさくらでは何も変えず、消しても次にほかのサーバーへ広げるときに戻すことになる。
- cron の節：4 社の表を、さくらの記述に置き換える。
  - さくらでは、SSH の `crontab` で行を足せた。足した行は、管理画面の「スクリプト」→「CRON設定」にも出る（作者の試し。4 章）。公式のマニュアルには記載がない。
  - 管理画面の「CRON設定」でも登録できる（[CRONを設定したい](https://help.sakura.ad.jp/rs/2242/)）。管理画面から登録できるのは最大 10 個（同じページ）。
  - 管理画面で選べる最短の間隔は 2 分で、毎分は選べない。毎分（1 分）で足した行は、管理画面に出るが、管理画面で変えて保存しようとすると弾かれる（作者の試し）。管理画面でも変えられるようにしたいなら、間隔の問いに 2 以上を答える、と書く。
- README の 2 行も、`--url` を付けた形にし、「さくらのレンタルサーバで確かめています」と書く。
- 「FTP で置く」の節は変えない。

## 4. 作者のさくらでの試しで分かったこと（2026-11-25）

- サブドメインを足すときに、ドキュメントルートを指定できた（`re-buji.shimomo.net` → `~/www/re-buji/`）。公式のヘルプには、この指定の記載が見つからなかった。
- 独自ドメインの URL で、公開の確かめが通った。
- 受信サーバーは Courier-IMAP（`Courier-IMAP ready.`）。
- SSH の `crontab` で、cron の行を足せた（「✓ cron に足しました」）。足した行は、管理画面の「CRON設定」にも出た。
- 管理画面の「CRON設定」の最短の間隔は 2 分で、毎分は選べない。毎分で足した行を管理画面で変えて保存しようとすると、弾かれる。
- 設置を終えたあと、見張りの URL は 200 を返した（Claude が確かめた）。
- 作者は 0.3.9 を消し、この 0.4.0 を本番として `re-buji.shimomo.net` で使い始めた。

まだ確かめていないこと：
- 「HTTPS転送設定」をオンにして `http://` の URL を渡したとき、転送でパスが残るか（任意）。

## 5. 確かめ方 **[判断]**

少なくとも次を、テストで確かめる。

- `tests/Console/InstallCommandTest.php`、`tests/Install/ConsoleExposureTest.php`
  - 質問にディレクトリが出る（`--public` のとき、`--root` だけのとき）。
  - 手で入れた URL が 404 なら聞き直し、2 回目の URL が届けば続く。3 回とも届かなければ `GAVE_UP` で止まる。
  - `--url` の URL が 404 なら、聞き直さずに止まる。
  - 確かめの道が残る転送（`http://` から `https://`）は、転送先で続ける。手で入れたときと `--url` のとき。転送先がまた転送したら、届かなかったとして扱う。
  - 確かめの道が残らない転送は、届かなかったとして扱い、文に `from=console` が出ない。
  - どの出力にも `?from=console` が出ない。
  - 待ちの回ごとに、待っている行が出る。
- 返信の探し方（`SetupReplyFinder` と IMAP の層）
  - 既読の返信も見つかる。番号でも Message-ID でも見つかる。
  - 関係のない既読のメールは、取り出さない。
  - 検索の前に NOOP を送る（IMAP の層のテストで、送った命令の並びを見る）。
- テストメールの本文に、画面のボタンだけを前提にした文が残っていない。

## 6. builder に任せること

- 質問と文の細かな言い回し（3 章の例と同じ意味を保つ）。
- `reach` を URL の質問の直後に移すための、`InstallCommand` の中の並べ替え。
- 転送の答えの分け方を、`ConsoleExposure` に置くか `ExposureCheck` に置くか。
- 既読の返信を探すための、`Mailbox` の新しいメソッドの形と、受信サーバーでの絞り方（IMAP の `SEARCH` の条件）。

## 7. 版

作者の本番は、いま 0.4.0 の zip（main `dce1197` と同じもの）で動いている。`bin/upgrade.sh` は、版が同じなら上げない（`version_compare` で新しいときだけ）。だから、この変更を 0.4.0 のまま出すと、作者の本番には届かない。この変更は **0.4.1** で出す。**[判断]**

0.4.0 は、main の今のもの（`dce1197`）を、この変更の前にそのまま出す。**[決定]**（2026-11-25、案 1）作者の本番と同じものが、署名つきのタグと sha256 で残り、README の `install.sh` の取り先もすぐに通る。ノートに、この設計で直す問題を「分かっている問題」として書く。

選ばなかった案 2：0.4.0 は出さず、この変更を 0.4.1 として出す。問題のある版を公開しないが、作者の本番がどのリリースとも合わない 0.4.0 になり、公開の版が 0.3.9 から 0.4.1 に飛ぶ。
