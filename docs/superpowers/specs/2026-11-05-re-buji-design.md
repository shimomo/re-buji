## 1. 何を作るか

地震が起きたら従業員にメールで知らせ、その**メールへの返信だけで無事を確かめる**安否確認システム。OSS として公開する。**[決定]**

- 対象は、BCP（事業継続計画）のために安否確認のツールを入れたいが、費用をかけられない組織。その組織が自分のレンタルサーバーに設置して使う。**[決定]**
- 作者はサービスを提供しない。作者自身が実際に運用する予定もない。**[決定]**
- 既存の有料サービスは月 6,800 円〜4 万円程度（トヨクモ、エマージェンシーコールなど）。その代わりになる選択肢を目指す。
- 地震の情報は、作者の OSS ライブラリ jmaxml/*（Packagist で公開済み、0.1.1、PHP ^8.3）から得る。
  - `jmaxml/feed`：気象庁のフィードを取得し、新しい電文を返す
  - `jmaxml/earthquake`：電文を地震イベントにまとめ、市町村ごとの震度を判定する
  - `jmaxml/codes`：市町村・細分区域などのコード表
- ライブラリのリポジトリは github.com/shimomo/jmaxml-php。設計書は `docs/superpowers/specs/2026-11-03-jmaxml-php-design.md`。

### 使う場面

1. 大きな地震が起きる。気象庁が震度速報、続いて震源・震度に関する情報を出す。
2. 登録した市町村が基準の震度以上になった従業員に、Re:無事 がメールを送る。
3. 従業員がそのメールに返信する。本文は空でもよい。怪我などがあれば本文に書く。
4. 事業を続けるかどうかを判断する責任者が、管理画面で「返信なし」と「要確認（本文あり）」の人を確かめる。

### 成功とは

設置した組織で、揺れた地域の従業員にもれなく連絡が届くこと。責任者が、返事の無い人と問題を抱えた人を数分で把握できること。

### アンチゴール（動いていても失敗とみなすこと）

- **揺れた地域の従業員に連絡が届かない。** いちばん困る失敗。次の場合も含む。
  - cron が止まっていることに誰も気づかない
  - メールの上限で送信が止まっていることに誰も気づかない
  - 登録した市町村コードが判定に使えない
- **誤報。** 訓練の電文や取り消された電文で連絡してしまう。
- **連絡が取れていないのに「無事」と数える。** 不在の自動応答や、宛先不明で戻ってきたメールを無事として扱うこと。
- **設置できない。** 最も安いレンタルサーバーのプランで動かない。

### 非ゴール（v0.1 ではやらない）

- 地震以外（津波、大雨、特別警報など）。jmaxml/earthquake の範囲に合わせる。
- LINE やアプリでの通知。後で足せるように設計だけはしておく（5.7）。
- 従業員本人のログイン、本人による登録（私用のアドレスや自宅を本人が足す機能）。
- 掲示板、メッセージ、家族の安否、部署ごとに見られる範囲を分ける権限。
- 英語の画面。画面は日本語だけ。

## 2. 制約

### 2.1 設置先：レンタルサーバー（最も安いプランを含む）**[決定]**

PHP を選んだのはレンタルサーバーで動かすため。DB も SSH も無い最安のプランまで対象にする。

2026-11-05 に各社の公式の仕様で確かめた制約：

| プラン | PHP | MySQL | SSH | cron | メール送信の目安 |
|---|---|---|---|---|---|
| ロリポップ エコノミー（月 121 円〜） | 8.4 あり | なし | なし | 1 件・5 分ごと | 100 通/時 |
| ロリポップ ライト | 8.4 あり | 50 | なし | 5 件・5 分ごと | 300 通/時 |
| ロリポップ スタンダード以上 | 8.4 あり | 100〜 | あり | 10 件・1 分ごと | 1,000 通/時 |
| さくら スタンダード以上 | **最新 8.3** | 50〜 | あり | 10 件（SSH の crontab なら緩い） | 15 分に 100 通程度 |
| さくら ライト | ― | なし | なし | **なし** | ― |
| エックスサーバー（全プラン） | 8.4 あり | 無制限 | あり | あり | 1,500 通/時 |
| ConoHa WING（全プラン） | 8.4 あり | 無制限 | あり | あり | 記載なし |

ここから決まる制約：

- **PHP 8.3 以上**。さくらのスタンダードは 8.3 が最新なので、PHP 8.4 にしか無い機能は使わない（jmaxml も 8.3 に下げた）。**[決定]**
- **SSH が無くても設置できる。** composer を動かせないので、`vendor/` まで含めた zip を配る。設置は FTP でアップロードし、初期設定はブラウザで行う。
- **cron は 1 本、5 分ごとでも動く。** ロリポップのエコノミーは cron を 1 件しか置けず、最短 5 分ごと。cron にはコマンドではなく PHP ファイルを指定する形にも合わせる。
- **DB は SQLite を標準とし、MySQL も選べる。** **[決定]**
  - SQLite は WAL を使わず、標準のジャーナルにする。ホームディレクトリがネットワークのファイルシステム（NFS）の上だと、WAL は壊れやすい。**[判断]**
  - DB ファイルは公開ディレクトリの外に置く。
- **メールの送信には上限がある。** 1 時間に送ってよい通数を設定でき、超えないように少しずつ送る（5.3）。
- **PHP の拡張は、レンタルサーバーで普通に使えるものだけに頼る。** ext-imap は PHP 8.4 で本体から外れ、無いことがあるので使わない。**[判断]**
- **最初の連絡が届くまで最大 5 分ほど遅れる**（cron が 5 分ごとの場合）。人数がメールの上限を超えると、最後の人にはさらに遅れて届く。安いプランが向くのは小さい組織（数十人まで）。README に書く。

### 2.2 作り方 **[決定]**

- **Slim 4** で作る。Laravel は `vendor/` が約 7,300 ファイル（53 MB）になり、FTP でのアップロードが重い。作者は Slim 2・3 の経験がある。
- **IMAP は自前で書く。** 必要な操作は、ログイン、未読の検索、取得、既読の印くらい。メールの中身の解析だけを `zbateson/mail-mime-parser` に任せる。IMAP のライブラリ（directorytree/imapengine）は Carbon や illuminate/* を引き込み、ファイル数が 2 倍になる。

2026-11-05 に測った構成（PHP 8.3、`--no-dev`）：

| パッケージ | 役割 |
|---|---|
| `slim/slim` ^4、`slim/psr7`、`php-di/php-di` | 本体、PSR-7、DI |
| `league/plates` ^3 | テンプレート |
| `slim/csrf` | CSRF 対策 |
| `symfony/mailer` ^7.4 | メール送信（8 系は PHP 8.4 が必要） |
| `symfony/http-client` ^7.4、`nyholm/psr7` | jmaxml/feed に渡す PSR-18 クライアントと PSR-17 ファクトリ |
| `jmaxml/earthquake`、`jmaxml/feed` ^0.1.1 | 地震の情報（core と codes は依存で入る） |
| `zbateson/mail-mime-parser` ^3 | 受信したメールの解析 |

これで `vendor/` は約 1,460 ファイル（12 MB）。依存を足すときは、ファイル数の増え方を確かめる。

- ライセンスは MIT。リポジトリは `github.com/shimomo/re-buji`。**[決定]**
- 名前は「Re:無事」（ローマ字表記は Re:Buji）。返信メールの件名に付く「Re:」と「無事」を合わせ、返信するだけで無事が伝わることを表す。**[決定]**

## 3. 登録

### 3.1 従業員 **[決定]**

管理者が、画面から 1 人ずつ、または CSV でまとめて登録する。従業員はログインしない。

| 項目 | 内容 |
|---|---|
| 名前 | 必須 |
| メールアドレス | 1 件以上、複数可。全部に送る **[判断]** |
| 所属 | 部署など。自由な文字列 **[判断]** |
| 市町村 | 1 件以上、複数可。それぞれに「勤務地」「自宅」のような名前を付けられる |
| メモ | 自由な文字列 |
| 有効／停止 | 停止中の人には送らない |

- **市町村で登録する。** 細分区域（188）や都道府県ではない。**[決定]**
  - 最も細かく判定でき、従業員にとっても自分の市町村は分かりやすい。
  - 細分区域でしか震度が出ない最初の震度速報にも、市町村から細分区域を引いて対応する（jmaxml/earthquake の `citiesAtLeast()` が行う）。
- 画面では、都道府県を選んでから市町村を選ぶ。
- CSV では、気象庁の市町村コード（7 桁、例 `1310100`）で指定する。名前だけだと、気象庁の表記（「仙台青葉区」）と一般の表記（「仙台市青葉区」）が食い違うため。**[判断]**
- `EarthquakeCodes::city()` が `null` を返すコードは、登録の時点で拒む。政令指定都市の市全体のコードや、合併・区の再編で無くなったコードがこれに当たる。jmaxml/codes の README にある注意。
- コード表を更新した版の Re:無事 に上げたら、登録済みのコードを確かめ直し、判定できない人を管理画面に出す。**[判断]**

### 3.2 管理者 **[判断]**

- ログインするのは責任者などの管理者だけ。複数人を登録でき、v0.1 では全員が同じ権限。
- ID（メールアドレス）とパスワードでログインする。パスワードは `password_hash()` で保存する。
- ログインに続けて失敗したら、受け付けを遅らせる。
- フォームには CSRF 対策をする。HTTPS は、レンタルサーバーの無料の SSL を前提にする。

## 4. 連絡を送る条件

- **しきい値**は組織ごとに設定する。既定は震度 5 弱以上。登録した市町村のどれかが基準に達した人に送る。**[判断]**
  - 判定は `EarthquakeEvent::citiesAtLeast()` に任せる。未入電（震度 5 弱以上と推定されるが、まだ観測が届いていない）の市町村も対象に含まれる。
- **運用種別が「通常」の電文だけを使う。** 気象庁の訓練・試験の電文では送らない（jmaxml/feed と jmaxml/earthquake の既定）。**[決定]**
- **取消**された地震では、まだ送っていない連絡を送らない。すでに送った人に取消を知らせるかは 9 章。
- **送るまでの待ち時間**を設定できる。既定は短め（9 章）。トヨクモは誤報を避けるため 10 分待つが、jmaxml は取消の電文を扱えるので短くてよい。**[判断]**
- **1 つの地震につき、1 人に 1 通。** 後から届いた電文で対象が増えたら（震度速報の後の震源・震度に関する情報、より新しい震度速報など）、増えた人に送る。**[判断]**
- **再送。** 返信の無い人に、決まった回数を決まった間隔で送り直す。既定は 3 回・1 時間ごとで、設定で変えられる。件名に【再送】を付ける。**[判断]**
- **近い時間の地震。** まだ返事をしていない人が、すぐ後の関連しそうな地震（`EarthquakeEvent::isPossiblyRelatedTo()`）でも対象になったら、2 通目は送らず、前の連絡に含める。**[判断]**
  - 時間をおいた本震は、別の地震として改めて送る。前震で無事と返した人が、本震で被災することもある。
- **訓練。** 管理者が画面から「訓練」の一斉送信をできる。対象は全員、または選んだ人。件名と本文に訓練と明記する。結果は本番と同じ画面で、訓練として区別して見られる。**[判断]**

## 5. 連絡と返事

### 5.1 送るメール **[判断]**

- 件名に、送信ごとの番号を入れる（例：`[安否確認 #a1b2c3d4] 地震がありました（宮城県沖・最大震度 6 弱）`）。
- Message-ID は、送信ごとに推測できない値にする。
- 本文には次のことを書く。
  - このメールに返信すれば無事として記録されること
  - 本文は空でよいこと
  - 怪我や出社できないなどの事情は本文に書くこと
  - 対象になった市町村と震度
- 文面は管理者が編集できる。既定の文面を用意する。
- 送信は SMTP。組織のレンタルサーバーのメールアカウントを使う。

### 5.2 返事の受け取り **[決定]**

- 組織に、返信を受ける専用のメールアドレスを 1 つ作ってもらう（例：`anpi@example.co.jp`）。
- cron の毎回、そのメールボックスを IMAP（TLS）で読みに行く。安いプランではメールをスクリプトに渡す設定（パイプ）が使えないので、読みに行く形にする。
- **誰の・どの地震への返事か**は、次の順に決める。**[判断]**
  1. 返信の `In-Reply-To` と `References` が、こちらの Message-ID と一致するか
  2. 件名に番号があるか
  3. 送り主のアドレスが登録済みか。登録済みなら、その人の直近の未回答の連絡に結び付ける
  4. どれでも決まらなければ、「照合できなかったメール」として管理画面に出す
- **本文**は、引用された元のメール（`>` の行、「〜は書きました」以下、署名の区切り以下）を取り除いた部分だけを記録する。空なら「無事」だけ。
- 読んだメールには既読の印を付け、二度は数えない。メールボックスからは消さない。**[判断]**
- **無事と数えないもの**（アンチゴールのため）：
  - 不在の自動応答。`Auto-Submitted`、`X-Autoreply`、`Precedence: auto_reply/bulk/junk` のようなヘッダーや、件名の「自動応答」「不在」で見分ける。「返信なし（自動応答だけ）」として扱う。
  - 宛先不明などで戻ってきたメール（MAILER-DAEMON、`Content-Type: multipart/report` など）。その宛先を「届かなかった」とし、責任者に見えるようにする。複数のアドレスのうち 1 件でも届けばよい。
- **なりすまし**（送り主の偽装）は、安否確認の性質上、大きな害は無いと見て受け入れる。**[決定]**

### 5.3 送信の上限と順番 **[判断]**

- 1 時間に送ってよい通数（例：ロリポップのエコノミーなら 100）を設定する。初期設定で、サーバーごとの目安を示す。
- cron の回ごとに、直近 1 時間の送信数が上限を超えない範囲で送る。残りは「送信待ち」として次の回に回す。
- 送る順番は、強く揺れた市町村の人から。同じなら、登録順。
- 上限に達して送れていない人がいることは、管理画面に出す。

### 5.4 代理回答 **[判断]**

管理者が、電話などで確かめた人の状態を代わりに記録できる（無事、要確認、本文）。記録したのが誰かも残す。

### 5.5 状態

1 人・1 地震（または訓練）ごとに、次の状態を持つ。

- 送信待ち／送信済み（何回目か）／届かなかった
- 返信なし／自動応答だけ／無事（空の返信）／要確認（本文あり）／確認済み（管理者が読んだ）／代理回答

### 5.6 責任者の画面 **[決定]**

地震のあとに管理画面を開いたとき、上から順に次のものを並べる（作者が確かめた画面の例に沿う）。

1. どの地震か（発生時刻、震源、マグニチュード、最大震度）、判定に使った電文、対象の条件、通常か訓練か
2. 人数：対象、返信なし、要確認、無事
3. **返信なし**の人：名前、所属、市町村と震度、理由
   - 理由は「届かなかった」「自動応答だけ」「送信済み・再送の時刻」「送信待ち（上限のため、予定時刻）」
4. **要確認**の人：返信の本文。「確認済みにする」で一覧から外せる
5. **無事**の人：人数だけを出し、開けば一覧が見える

「怪我」などの言葉による自動の振り分けはしない。「無事です、怪我もありません」のような返信を取り違えるので、本文のある返信はすべて要確認とし、判断は責任者が本文を読んで行う。**[判断]**

### 5.7 経路の抽象化 **[決定]**

「連絡を送る」「返事を受け取る」を経路ごとの部品にする。v0.1 はメールだけ。LINE などを後で足すとき、判定・状態・画面は変えずに済むようにする。

## 6. 運用

### 6.1 cron **[判断]**

- cron に登録するのは、公開ディレクトリの外にある PHP ファイル 1 本（例：`bin/cron.php`）。
- その 1 本が、毎回次のことを順に行う。
  1. フィードを確認する（`FeedClient::poll()`）
  2. 新しい電文を地震イベントにまとめる（`EarthquakeEvents::group()`）
  3. 送る相手を決める
  4. 上限の範囲でメールを送る
  5. 返信を読む
  6. 再送する
- 5 分ごとを基本とし、1 分ごとに動かせるサーバーではそうする。jmaxml/feed の抜けの判定（8 分）に収まる。
- 前の回がまだ動いている間は、次の回を始めない（ロックファイル）。
- 1 回の処理は短く保つ。レンタルサーバーは、重い cron を止めることがある。
- 電文は、地震を作り直すために一定期間 DB に残す。jmaxml の設計どおり、地震イベントは電文から毎回作り直す。

### 6.2 止まっていないかの見張り **[決定]**

- 管理画面の上部に、最後にフィードを確認した時刻を出す。15 分以上空いたら警告する。
- 次のことを、画面と管理者へのメールで知らせる。
  - フィードの抜け（jmaxml/feed の `gap`。追いつけなかった場合）
  - 送信の失敗、受信の失敗
  - 上限による送信待ちの発生
- 定期的な無事のメール（ハートビート）を管理者に送るかは 9 章。

### 6.3 設置と初期設定 **[決定]**

1. zip を展開して FTP でアップロードする。公開ディレクトリには `public/` の中身だけを置く。それ以外は外に置く。
2. ブラウザで初期設定の画面を開き、次のことを行う。
   - DB を選ぶ（SQLite か MySQL）
   - 送信（SMTP）と受信（IMAP）のメールアカウントを登録する
   - 1 時間あたりの送信の上限としきい値を決める
   - 最初の管理者を作る
3. 最後に、自分宛てにテストメールを送り、それへの返信を読めることまで確かめる。ここが通らないと、初期設定を終えられない。
4. cron の登録方法を、サーバーごとに画面で案内する。

設定とデータ（DB、設定ファイル、ロック）は、上書きされない場所に置く。

### 6.4 バージョンアップ **[決定]**

新しい zip を FTP で上書きする。DB の変更は、管理画面から 1 回のボタンで当てる。適用済みの変更は DB に記録し、二度は当てない。

### 6.5 個人情報 **[判断]**

- 名前、メールアドレス、市町村は、公開ディレクトリの外の DB にだけ置く。
- 受信したメールの本文は、安否の記録として保存する。
- 古い地震の記録を消す機能を管理画面に置く。

- ログイン

- 訓練の送信
- 設定（しきい値、待ち時間、再送、上限、メールの文面、SMTP と IMAP）
- 照合できなかったメールの一覧
- 管理者の一覧
- 見張り（6.2）の状態

## 8. 設計者に任せること

- ディレクトリ構成、クラスとテーブルの設計、ルーティング
- DB の変更の仕組み（SQLite と MySQL の両方で動くこと）
- 自前の IMAP の実装の細部と、テスト用の偽の IMAP サーバー
- 画面の見た目（作者が確かめた画面の例に沿うこと）
- 既定の文面
- 配布用の zip の作り方（GitHub のリリースに置く）

## 9. 未決事項

- 送るまでの待ち時間の既定値（0 分か、2 分程度か）
- 取消になった地震で、すでに送った人に取消を知らせるか
- 定期的な無事のメール（ハートビート）を管理者に送るか
- 1 人あたりのメールアドレスの上限
