**Goal:** 地震の最中に管理者が見る画面を正しくし、記録を失わないようにして、v0.1.7 を出せる状態にする。5 件は作者が選んだ。

**Architecture:** 機能は足さない。DB の形も変えない。送信待ちの時刻は「その人のアドレスの数だけ空く時刻」で出す。判定の元は読めた電文から選ぶ。判定し直しても前に一致した市町村は残す。地震を消すときは、まとめた連絡へ答えを渡してから消す。「DB の更新」を押したら、待っている知らせを消す。

**Tech Stack:** 計画 11 と同じ。依存は増やさない。

**Spec:** `docs/superpowers/specs/2026-11-05-re-buji-design.md`（4 連絡を送る条件、5.3 送る通数の上限、6.2 画面、6.4 バージョンアップ、6.5 記録の削除）

**前の計画：** `docs/superpowers/plans/2026-11-19-re-buji-v0.1.6.md`（PR #13 でマージ済み。v0.1.6 はリリース済み）。直すのは次の 5 件。作者が 2026-11-20 に選んだ。

## Global Constraints

- 計画 1〜11 の Global Constraints をすべて引き継ぐ。主なもの：
  - PHP `^8.3`、SQLite の PRAGMA、UTC の時刻の文字列、名前空間、`.htaccess`
  - `setUp` / `tearDown` を使わない。テストでは、日付に依る値に `FrozenClock` を使う
  - コミットメッセージの末尾に `Co-Authored-By` を付ける
  - Psalm errorLevel 1、Pint
  - `src/php-version.php`、`public/index.php`、`bin/cron.php` は PHP 5.5 以降で読める構文のまま（CI の `old-php` が確かめる）
- DB の形は変えない（マイグレーションを足さない）。v0.1.6 から上げたときに「DB の更新」を押さなくて済むようにするため
- 依存を増やさない
- SQL は SQLite と MySQL の両方で動く書き方にする（MySQL は、更新する表を同じ文の副問い合わせで読めない）
- 画面の文言は、今のものを変えない（出す時刻と、出す場面だけを直す）

## Review Focus

- 管理者への知らせの分（予備の枠）まで使い切っている → 次に送れる時刻は、足りない通数だけ古いメールが 1 時間の枠から抜ける時刻（Task 1）
- 後の電文が、前に一致した市町村の震度を下げた（まだしきい値以上）→ 一覧のその市町村は新しい震度になる（Task 3）
- まとめた先の連絡に、まだ答えが無い → まとめた連絡は今までどおりで、壊れない（Task 4）
- 消す地震に、2 つの地震の連絡がまとめられている → どちらにも答えが渡る（Task 4）
- 「DB の更新」を押したとき、cron の別のエラーが出ていた → そのエラーは消さない（Task 5）

**Interfaces:**
- 送る側（`NotificationSender::deliver()`）は、`remaining() >= その人のアドレスの数` のときだけ送る。表示と見張りを、これに合わせる
- `MessageRepository::nthAttemptSince(DateTimeImmutable $since, int $n): ?DateTimeImmutable`：`$since` より後の `attempted_at` を古い順に並べた n 番目（1 から）。足りなければ null
- `RateLimit::nextSlotFor(DateTimeImmutable $now, int $mails): ?DateTimeImmutable`：`remaining($now) >= $mails` なら null（次の cron で送れる）。そうでなければ、`$k = $mails - remaining($now)` として、`nthAttemptSince($now->modify('-60 minutes'), $k)` の 60 分後
- `RateLimit::nextSlotAt($now)` は `nextSlotFor($now, 1)` を返す（今の呼び出し元は Task のなかで置き換えるが、名前は残す）
- `NotificationRepository::fewestAddressesWaiting(DateTimeImmutable $now): ?int`：`countWaiting()` と同じ条件の連絡のうち、人のアドレスの数がいちばん少ない数。無ければ null。`employee_emails` を `employee_id` で数え、連絡ごとに GROUP BY した数の MIN（従業員が消えた連絡は数えない）
- `EmployeeRepository::addressCount(int $id): int`：その人の `employee_emails` の数
- `HomeController`：`$nextSlot` は、`fewestAddressesWaiting()` が null なら null、そうでなければ `nextSlotFor($now, その数)`。テンプレートと文言は今のまま
- `QuakeBoard::build()`：送信待ち（`PENDING` で `notBefore` が今以前）の連絡は、その人の `addressCount()` で `nextSlotFor()` を呼んだ結果を `reason()` に渡す（同じ数は 1 回だけ問い合わせる）。従業員が消えた連絡は 1 通として扱う。`QuakeBoard` の constructor に `EmployeeRepository` を足す
- `WatchJob`（182 行目）：「上限による送信待ち」の判断も、`fewestAddressesWaiting()` と `nextSlotFor()` を使う
